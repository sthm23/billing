## Решения владельца продукта

1. **Два уровня категорий.**
   - Уровень 1 — направление магазина (Fashion, Electronics, Lumber…). Его выбирает админ при создании магазина (`POST /admin/stores`), связь через `CategoriesOnStore`.
   - Уровень 2 — категории товаров внутри направления (Платья, Обувь, Брус…).
2. **Единый справочник для всех магазинов** (вариант «а»). Подкатегории общие: магазины одного направления видят и используют подкатегории друг друга — так и задумано.
3. **Подкатегории создают владелец магазина (staff OWNER) или платформенный ADMIN.** Принцип «найти или создать», как у брендов.
4. **Дерево чинит сама миграция, без ручной правки прода** (2026-11-13, заменяет прежнее «прод правится вручную»). На проде 1 магазин, его направление — Lumber (древесина). Подкатегории Lumber уже 2-уровневые, а Fashion/Electronics на проде не используются. Поэтому миграция сразу выравнивает дерево до 2 уровней и удаляет промежуточные Men/Women.
5. **Подкатегория у товара обязательна** (2026-11-13): `Product.categoryId` всегда указывает на категорию уровня 2 под направлением магазина. Сохранить товар только с направлением нельзя.
6. **Rename + delete в v1, только ADMIN** (2026-11-13). Удалять можно, только если у подкатегории нет товаров. Объединение (merge) в v1 не делаем.
7. **`createdById` у категории — да** (2026-11-13): nullable FK на `User`. У системных категорий из сида null.
8. **У магазина одно направление** (2026-11-13). Схема (`CategoriesOnStore`) по-прежнему допускает несколько, но UI и логика рассчитаны на одно. Если направлений окажется несколько, берём все: бэкенд проверяет «подкатегория под любым из направлений магазина».
9. **Сид — всё на уровне 2, каждая категория один раз** (2026-11-13, уточнено владельцем). Бывшие уровни 3 и 4 поднимаем на уровень 2, никого не удаляем, кроме промежуточных Men/Women. Дубли (повтор Shoes, Accessories… под Women) убираем:
   - **Fashion** → Shirts, T-Shirts, Pants, Sportswear, Shoes, Sneakers, Boots, Formal Shoes, Accessories, Outerwear, Underwear, Socks, Hats, Dresses, Tops, Bottoms;
   - **Electronics** → Phones, Smartphones, Laptops;
   - **Lumber** → Beam, Timber, Batten, Roofing, Wood Panels (без изменений).
10. **Названия — в БД, русский основной + переводы** (2026-11-13). `name` — русское название (основное, по нему уникальность), `nameUz` и `nameEn` — nullable переводы. Сид заполняет все три, у созданных владельцем только `name`. Клиент показывает имя на языке приложения, а если его нет — `name`. Английские ключи (`CategoryEnum`) и блок `category` в переводах мобилки уходят.

## Целевая модель

- `Category` уровня 1: `parentId = null`, системные (сид), их создаёт только ADMIN (новых направлений через приложение пока не нужно).
- `Category` уровня 2: `parentId` = id направления, глубже не бывает.
- Уникальность: **название уникально внутри родителя**, без учёта регистра. Одна и та же «Обувь» может быть и в Fashion, и в другом направлении.
  - Prisma: `@@unique([parentId, name])` вместо `name @unique`.
  - Postgres не считает `NULL` равными, поэтому для корня нужен частичный индекс `UNIQUE (lower(name)) WHERE "parentId" IS NULL`. Регистронезависимость для детей: `UNIQUE ("parentId", lower(name))` (индексы руками в SQL миграции) + поиск `mode: 'insensitive'` в сервисе.
- `createdById String?` → `User` (`onDelete: SetNull`), обратная связь в `User`.
- `nameUz String?`, `nameEn String?`. Чтобы «найти или создать» не находил две категории сразу, переводы тоже уникальны внутри родителя без учёта регистра: частичные индексы `UNIQUE ("parentId", lower("nameUz")) WHERE "nameUz" IS NOT NULL` (и так же для `nameEn`, и для корня).
- Поиск («найти или создать», поиск в листе выбора) сравнивает ввод со всеми тремя полями: «Poyabzal», «Shoes» и «обувь» найдут одну и ту же «Обувь».

## Этапы

### Этап 1 — Схема и сид
1. Миграция, одна, в таком порядке (SQL руками):
   1. **Выравнивание данных**: рекурсивным CTE каждой категории глубже 2-го уровня ставим `parentId` = id её корня (Shoes, Sneakers… → Fashion, Smartphones → Electronics). Конфликтов имён не будет: до миграции `name` уникально глобально.
   2. **Удаление промежуточных**: `DELETE` категорий уровня 2, у которых после шага 1 нет детей и нет товаров, и только с именами `Men`/`Women` (жёсткий список, чтобы не задеть пустые подкатегории Lumber). Если на Men/Women вдруг есть товары, строка останется — FK не даст потерять данные.
   3. Схема: добавить колонки `nameUz`, `nameEn`, `createdById` + FK.
   4. **Перевод названий**: `UPDATE ... FROM (VALUES ('Shoes','Обувь','Poyabzal'), ...)` — `nameEn` = старый ключ, `name` = русский, `nameUz` = узбекский. Таблица соответствий — та же, что в сиде (решение 9, все 3 направления). Строки, которых нет в таблице (созданные вручную), не трогаем.
   5. Индексы: убрать `categories_name_key`, добавить `@@unique([parentId, name])` и частичные регистронезависимые индексы из «Целевой модели».
2. Переписать сид на 2 уровня по решению 9: вместо `CategoryEnum` — список `{ name, nameUz, nameEn }`. Русский и узбекский берём из текущих переводов мобилки, исправляя ошибки: Timber/Roofing в uz — латиницей; у Shirts/Dresses и Tops/Outerwear — разные uz-названия. **Готовый список ru/uz показать владельцу на проверку до миграции.**
3. Upsert в сиде делать по (`parentId`, `name`): для корня `findFirst` + `create`, потому что Prisma не умеет upsert по составному ключу с `null`. Сид идемпотентен: повторный запуск на уже выровненной базе ничего не меняет.
4. Проверка локально, два сценария:
   - копия старой базы (3 уровня) → `prisma migrate deploy` → дерево 2 уровня, Men/Women нет, названия русские с переводами, товары на месте;
   - `prisma migrate reset` + сид → то же дерево.
5. Прод: ручных действий нет, миграция применяется при деплое. Перед деплоем полезно проверить одним `SELECT`, что на проде нет товаров с категориями Fashion/Electronics (ожидаем 0, магазин — Lumber).

### Этап 2 — Backend API (`src/category-attributes/`)
1. `GET /category/:storeId/categories` → 2 уровня (направления + подкатегории), сортировка по `name`. Каждая категория отдаётся с `name`, `nameUz`, `nameEn` — язык выбирает клиент. Так же — `GET /category` (корни для формы создания магазина). Проверку `ownStore` оставить.
   - Товары (список, карточка): строка `category` остаётся (теперь русское имя — совместимость с web), рядом добавляется `categoryI18n: { name, nameUz, nameEn }`.
2. **Новый** `POST /category/subcategory` `{ parentId, name }`:
   - кто: staff OWNER своего магазина или ADMIN, остальные получают 403;
   - `parentId` должен быть категорией уровня 1, иначе 400. У OWNER она должна быть направлением его магазина (`CategoriesOnStore`), иначе 403;
   - найти или создать: trim, поиск без учёта регистра по `name`/`nameUz`/`nameEn` внутри `parentId`; повторный вызов возвращает существующую. Новая создаётся только с `name` (введённая строка как есть). Гонку P2002 обработать повторным поиском;
   - валидация длины (2–50); `createdById = user.id`.
3. **Новые, только ADMIN** (`AdminGuard`):
   - `PATCH /category/subcategory/:id` `{ name?, nameUz?, nameEn? }` — только для уровня 2; так админ дописывает переводы к категориям, созданным владельцами. При конфликте любого из имён внутри того же направления (без учёта регистра) — 409;
   - `DELETE /category/subcategory/:id` — только для уровня 2. Если есть товары (`products` count > 0), вернуть 400 с понятным сообщением.
4. `ProductService.create` и `update`: `categoryId` обязана быть уровня 2, а её `parentId` должен входить в `CategoriesOnStore` магазина пользователя, иначе 400. Проверку делать **до** `try`, чтобы не потерять код (см. «Error wrapping» в `billing/AGENTS.md`). Название для `buildSku` брать из БД (`name`, русское; `skuToken` сохраняет кириллицу — у новых товаров токен категории в SKU будет русским, существующие SKU не меняются). `CreateProductDto.category` сделать `@IsOptional` и игнорировать (на переходный период его ещё шлют web/старые клиенты), позже удалить.
5. Фильтр списка товаров: «сама категория + её дети» (чип-направление → все подкатегории, чип-подкатегория → только она).
6. Тесты (паттерн `src/product/product.service.spec.ts`):
   - подкатегории: find-or-create, регистр/trim, чужое направление → 403, уровень 2 как parent → 400, SELLER → 403, P2002 → возврат существующей;
   - rename: конфликт → 409, rename корня → 400; delete с товарами → 400;
   - создание и изменение товара: уровень 1 → 400, подкатегория чужого направления → 400, SKU строится из имени в БД;
   - фильтр списка по направлению и по подкатегории.

### Этап 3 — Mobile
1. Сервис/хуки: `getStoreCategories` (2 уровня), `createSubcategory`, `renameSubcategory` / `deleteSubcategory` (admin), инвалидация query-ключей категорий.
2. Лист выбора категории (bottom sheet по образцу `BrandSheet` из `screens/admin/shops/NewShopSheets.tsx`): подкатегории направления магазина + поиск + «Добавить «…»» для OWNER/ADMIN. Кнопку прячет `libs/roles.ts`, реальная проверка — на бэкенде.
3. Использовать лист в форме товара, когда она появится (экрана создания товара в mobile пока нет — это отдельная задача). До этого лист живёт как готовый компонент.
4. Список товаров (`ProductListScreen`): чипы показывают подкатегории направления магазина.
5. Карточка магазина у админа (`AdminShopScreen`): блок «Каталог» со списком подкатегорий направления, у каждой rename/delete (ADMIN). Здесь же — единственное место для чистки дублей в v1.
