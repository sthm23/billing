# Категории товаров — план исправления

> Статус: план согласован 2026-11-12, реализация не начата (будет в отдельном чате).
> Читать вместе с: `docs/features/products.md` («Categories and Attributes»), `docs/security.md`, `billing/docs/DATABASE.md`.

## Решения владельца продукта

1. **Два уровня категорий.**
   - Уровень 1 — направление магазина (Fashion, Electronics, Lumber…). Его выбирает админ при создании магазина (`POST /admin/stores`), связь через `CategoriesOnStore`.
   - Уровень 2 — категории товаров внутри направления (Платья, Обувь, Брус…).
2. **Единый справочник для всех магазинов** (вариант «а»). Подкатегории общие: магазины одного направления видят и используют подкатегории друг друга — так и задумано.
3. **Подкатегории создают владелец магазина (staff OWNER) или платформенный ADMIN.** Принцип «найти или создать», как у брендов.
4. **Данные на проде правятся вручную**, это делает владелец продукта (на проде 1 магазин). Миграция не обязана переносить данные — достаточно, чтобы схема применилась.

## Как сейчас (проверено по коду 2026-11-12)

| Где | Что |
|---|---|
| `prisma/schema.prisma` → `Category` | Дерево через `parentId`, **`name @unique` на всю таблицу**. |
| `prisma/seed/category.seed.ts` | **3 уровня**: Fashion → Men/Women → Shoes → Sneakers. Upsert идёт по `name` с `update: {}`. Поэтому Shoes, Accessories и другие у Women переиспользуют строку из Men: под Women их фактически нет, дерево сломано. |
| Названия | В сиде — английские ключи (`CategoryEnum`), клиент переводит их через `t('category.<name>', { defaultValue: name })` (mobile `ru.ts` → `category`). |
| `GET /category` | Только корневые категории (используется в форме создания магазина у админа). |
| `GET /category/:storeId/categories` | Направления магазина вместе с детьми и внуками (3 уровня). |
| `ProductService.create` | Сохраняет `categoryId` без проверки. Не проверяется ни то, что категория относится к направлению магазина, ни уровень категории. В DTO поле обязательное, а сервис пишет `dto.categoryId ?? null`. |
| `CreateProductDto.category` | **Строка от клиента**, используется в `buildSku(...)`. Клиент сам присылает название категории — так быть не должно. |
| `ProductService` (список товаров), фильтр `categoryId` | Ищет по самой категории, её детям и внукам (3 уровня). |
| Mobile | Чипы-фильтры в `ProductListScreen` строятся по категориям магазина. Сервис `createProduct` и хук `useCreateProduct` есть, **экрана создания товара нет**. |
| Web (`billing_ui`) | `product-create` выбирает категорию из `getStoreCategoryList`. Веб будет выведен из эксплуатации — только совместимость. |

## Целевая модель

- `Category` уровня 1: `parentId = null`, системные (сид), их создаёт только ADMIN (новых направлений через приложение пока не нужно).
- `Category` уровня 2: `parentId` = id направления, глубже не бывает.
- Уникальность: **название уникально внутри родителя**, без учёта регистра. Одна и та же «Обувь» может быть и в Fashion, и в другом направлении.
  - Prisma: `@@unique([parentId, name])` вместо `name @unique`.
  - Postgres не считает `NULL` равными, поэтому для корня нужен частичный индекс `UNIQUE (lower(name)) WHERE "parentId" IS NULL`. Регистронезависимость для детей: `UNIQUE ("parentId", lower(name))` (индексы руками в SQL миграции) + поиск `mode: 'insensitive'` в сервисе.
- Опционально (вопрос): `createdById` (User) у категории — для аудита, кто добавил подкатегорию.

## Этапы

### Этап 1 — Схема и сид
1. Миграция: убрать `categories_name_key`, добавить индексы из «Целевой модели».
2. Переписать сид на 2 уровня, без английских промежуточных Men/Women. Предлагаемый состав согласовать с владельцем (например, Fashion → Платья, Рубашки, Футболки, Брюки, Обувь, Аксессуары, Верхняя одежда…). Ключи `CategoryEnum` + переводы в mobile `ru/en/uz` (`category` блок) обновить.
3. Upsert в сиде делать по (`parentId`, `name`).
4. Прод: владелец сам переносит категорию магазина и товаров (дать ему SQL-подсказку в конце этапа).

### Этап 2 — Backend API
1. `GET /category/:storeId/categories` → возвращать 2 уровня (направления + подкатегории), отсортированные по имени. Проверку «свой магазин» (`ownStore`) оставить.
2. **Новый** `POST /category/subcategory` `{ parentId, name }`:
   - кто: staff OWNER своего магазина или ADMIN;
   - `parentId` — категория уровня 1; у OWNER она должна быть привязана к его магазину (`CategoriesOnStore`), иначе 403;
   - найти или создать без учёта регистра, trim; повторный вызов возвращает существующую (200), гонку P2002 обработать повторным поиском;
   - валидация длины (2–50).
3. Переименование и удаление подкатегорий — **только ADMIN** (справочник общий; удалять нельзя, если есть товары). Можно отложить, если не нужно в v1 (вопрос).
4. `ProductService.create` и `update`: `categoryId` обязана быть уровня 2 (или 1 — см. вопросы) и лежать под направлением магазина, иначе 400. Название категории для `buildSku` брать из БД, поле `CreateProductDto.category` убрать (web/mobile перестают его слать; на переходный период игнорировать).
5. Фильтр списка товаров: упростить до «сама категория + её дети».
6. Тесты: сервис подкатегорий (find-or-create, регистр, чужое направление → 403, уровень 2 как parent → 400), создание товара с неверной категорией.

### Этап 3 — Mobile
1. Сервис/хуки: `getStoreCategories` (2 уровня), `createSubcategory`, инвалидация.
2. Выбор категории (bottom sheet, по образцу `BrandSheet` из `screens/admin/shops/NewShopSheets.tsx`): список подкатегорий направления + поиск + «Добавить «…»» для OWNER/ADMIN (кнопку прячет `libs/roles.ts`, проверка — на бэкенде).
3. Использовать в форме товара, когда она появится (экрана создания товара в mobile пока нет — это отдельная задача; если она будет раньше, лист выбора категории делается внутри неё).
4. Список товаров: если у магазина одно направление — чипы показывают его подкатегории; если несколько — направления (как сейчас).
5. Карточка магазина у админа: блок «Каталог» — показывать подкатегории направления (по желанию).
6. Отображение: системные категории — через перевод `category.<name>`, пользовательские — как есть (`defaultValue`).

### Этап 4 — Web (минимально)
- Убедиться, что `product-create` работает с 2-уровневым ответом и без поля `category` (или продолжает его слать — бэкенд игнорирует). Новых функций не добавлять.
