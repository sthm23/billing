# Telegram-магазин (Mini App для магазина) — план

> Создан 2026-11-27. Статус: **план согласован (раунд 2), код не писался**; старт — по команде пользователя.
> Затрагивает: `billing` (основное), `billing-mobile` (управление + заявки), **новый репозиторий** с React Mini App.
> `billing_ui` (Angular) не трогаем — продукт переезжает на mobile/Expo web.

## Идея

Магазин создаёт своего Telegram-бота и вставляет его токен в sthm. У бота появляется кнопка «Магазин»,
которая открывает **один общий** React Mini App (шаблон для всех магазинов). Mini App показывает каталог
именно этого магазина. Покупатель собирает корзину и отправляет заявку. Продавец в sthm видит заявку,
звонит клиенту, подтверждает — и дальше обычный процесс sthm (заказ → скидка → оплата в магазине).
Клиент получает уведомление от бота.

## Решения (пользователь, 2026-11-27)

1. Заявка из Telegram — **черновик для сотрудника**, канал онлайн; продавец подтверждает, клиент получает уведомление.
2. **Оплаты в Mini App нет.** Клиент договаривается по телефону, приходит в магазин, платит там; скидку даёт сотрудник
   существующим способом (общая скидка на заказ, `docs/order-discount/PLAN.md`).
3. Каталог — **все товары магазина независимо от склада**. Если товар лежит на другом складе — менеджер делает
   перенос между складами (см. «Склады и перенос»).
4. Бота подключает **сам владелец** по инструкции в приложении; админ платформы тоже может (запасной путь).
5. У клиента спрашиваем **телефон, ФИО, область и район**.
6. Это **отдельная платная услуга** (флаг на магазине, включает админ).
7. Mini App — **отдельное React-приложение в отдельном репозитории**; хостинг пока на том же сервере
   (nginx, статика); разделение серверов обсудим позже, когда упрёмся в бюджет.

## Что уже есть в коде (проверено 2026-11-27)

- `Product`, `ProductVariant`, `Store` несут `storeId` → каталог магазина отдаётся без чужих данных.
- `OrderChannel.ONLINE` уже есть в enum, нигде не используется.
- `Order.warehouseId` и `Order.cashierId` **обязательные** → заявка не может быть «просто Order» (нет склада и сотрудника).
- `Customer` = `User` (телефон `@unique`) + `Customer`; `UserService.createCustomer` умеет брать существующего `User`
  и подключать клиента к магазину (`Store.customers`), но при уже существующем клиенте кидает 409.
- Остаток проверяется атомарно **только при оплате** (`Inventory.updateMany ... gte`), при создании заказа — нет.
  Значит, заказ можно создать и держать в HOLD без остатка на складе.
- Переноса между складами **нет** (`TRANSFER` в коде — только способ оплаты). Есть приходы/корректировки (`StockMovement`).
- Telegram-кода и шифрования секретов в `billing/src` нет — делаем с нуля.
- `ThrottlerGuard` не глобальный; в `billing/AGENTS.md` сказано: «не добавлять на другие маршруты без решения» (см. вопрос 6).
- Публичный маршрут = маршрут без `@UseGuards(AuthJWTGuard)`.

## Архитектура

```
Покупатель ─ бот магазина (кнопка «Магазин»)
   └→ Mini App (React, один на всех): https://shop.<домен>/<slug>
        └→ API  /public/tg/:slug/...   заголовок Authorization: tma <initData>
              • по slug → магазин → его токен бота → проверка подписи initData (HMAC)
              • отдаёт только данные этого магазина
        └→ POST /public/tg/:slug/orders  → создаётся OnlineOrder (NEW)
              └→ бот пишет магазину: «Новая заявка #…»
Продавец (billing-mobile) → «Онлайн-заявки» → звонит → «Подтвердить»
   └→ создаётся обычный Order (channel ONLINE, HOLD) + клиент → дальше как сейчас
   └→ бот пишет клиенту: «Заявка принята»  (или «отклонена»)
```

**Зачем токен бота бэкенду:** (1) настроить бота (`setWebhook`, `setChatMenuButton`); (2) проверять подпись `initData`
— так мы знаем, что запрос пришёл из Telegram, и от какого пользователя; (3) отправлять сообщения магазину и клиенту.

## Модель данных (предложение, перед миграцией читаем `docs/DATABASE.md`)

```prisma
model Store {
  ...
  /// Платная услуга «Telegram-магазин»; включает только платформенный ADMIN
  telegramShopEnabled Boolean @default(false)
  telegramBot         StoreTelegramBot?
  onlineOrders        OnlineOrder[]
}

model StoreTelegramBot {
  id              String   @id @default(uuid())
  storeId         String   @unique
  slug            String   @unique          // в URL Mini App, [a-z0-9_-]{3,32}
  botTokenEnc     String                    // AES-256-GCM, ключ в env; наружу не отдаётся
  botId           String                    // Telegram id бота (из getMe)
  botUsername     String
  webhookSecret   String                    // secret_token вебхука
  notifyChatId    String?                   // чат/группа, куда писать о новых заявках
  isActive        Boolean  @default(true)
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt
}

enum OnlineOrderStatus { NEW CONFIRMED REJECTED }

model OnlineOrder {
  id             String            @id @default(uuid())
  storeId        String
  number         Int                           // номер заявки в магазине (для уведомлений)
  telegramUserId String                        // кому слать уведомления
  fullName       String
  phone          String
  region         String                        // область (из справочника)
  district       String                        // район (текст)
  comment        String?
  status         OnlineOrderStatus @default(NEW)
  orderId        String?           @unique     // созданный Order после подтверждения
  customerId     String?                       // клиент, привязанный при подтверждении
  handledById    String?                       // staffId
  handledAt      DateTime?
  rejectReason   String?
  createdAt      DateTime          @default(now())
  items          OnlineOrderItem[]
  @@index([storeId, status, createdAt])
}

model OnlineOrderItem {
  id            String  @id @default(uuid())
  onlineOrderId String
  variantId     String
  quantity      Int
  priceAtRequest Decimal                     // цена, которую видел клиент (информация)
}
```

Почему **отдельная** `OnlineOrder`, а не `Order` со статусом: `Order` требует склад и кассира, а все отчёты
(`SOLD_ORDER_FILTER`, дашборд, сводки) завязаны на статусы `Order`. Отдельная сущность ничего не ломает:
в отчёты попадает только подтверждённый, уже обычный `Order`.

## Бизнес-правила

1. **Склад не списывается и не резервируется** ни при заявке, ни при подтверждении — только при оплате (как везде).
2. **Цена** в каталоге и в заявке — информационная; при подтверждении заказ берёт **актуальную** цену варианта.
   Клиентские цены и итоги никогда не считаются на клиенте как источник правды: Mini App показывает то, что отдал сервер.
3. В каталог попадают: не архивные, не черновые (`isDraft`) товары, варианты с `canSell = true`.
   Прокат (`canRent`) в Mini App не показываем.
4. **Остаток для клиента** считает бэкенд: сумма `Inventory.quantity` по всем складам магазина. Больше нуля —
   показываем число, ноль — «нет в наличии» (товар остаётся в каталоге, в корзину добавить можно: остаток проверится при оплате).
5. **Клиент (`Customer`) создаётся/привязывается при подтверждении**, а не при отправке заявки: публичный
   эндпоинт не должен создавать `User` по неподтверждённому телефону (мусор, подмена имён). При подтверждении
   сотрудник видит телефон: найден существующий клиент → привязываем и подключаем к магазину; нет → создаём.
   Имя существующего клиента **не перезаписываем**.
6. Подтверждение/отклонение: **OWNER, MANAGER, SELLER** магазина; заявка `NEW` обрабатывается один раз
   (повторное подтверждение → 409). Заказ создаётся на склад, который сотрудник выбирает из своих (владелец — любой).
7. Подтверждение создаёт `Order` (`channel = ONLINE`, `HOLD`), выбор склада — на сотруднике (по умолчанию склад,
   где есть остаток). Дальше сотрудник открывает заказ в обычном экране: скидка, оплата — как сейчас.
8. Магазин `SUSPENDED` или `telegramShopEnabled = false` → публичное API отвечает «магазин недоступен»; бот не отключаем.
9. Токен бота: хранится **только зашифрованным**, не логируется, **не возвращается** ни в одном ответе
   (в карточке — `@username` и «подключён»). Отключение магазина = снять webhook + удалить токен.

## Склады и перенос

Клиент видит все товары; продавец при подтверждении выбирает склад. Если нужного количества на этом складе нет,
остаток проверится только при оплате, поэтому порядок такой: заказ в HOLD → менеджер переносит товар →
оплата проходит.

**Рекомендация: одна операция «Перенос»** (а не два ручных движения): `StockMovement OUT` на складе-источнике +
`IN` на складе-приёмнике в одной транзакции, с общим `transferId`. Один шаг вместо двух, нельзя «забыть вторую половину»,
виден в аудите. Это **отдельная фича** (свой план `billing/docs/warehouse-transfer/PLAN.md`), **v1 Telegram-магазина её
не ждёт** — на старте менеджер может сделать вручную расход+приход. Перед планом перенос нужно сверить с модулем
`warehouse/` (там движения уже есть).

## Подключение бота владельцем (то, что покажем в инструкции)

Профиль → «Telegram-магазин» (виден владельцу, если админ включил услугу):

1. В Telegram открыть **@BotFather** → `/newbot` → имя бота → username (на `bot`).
2. BotFather пришлёт **токен** вида `123456:ABC...` → скопировать.
3. В sthm вставить токен и придумать **адрес магазина** (`slug`, например `baraka_888`).
4. sthm сам проверяет токен (`getMe`), шифрует, ставит webhook и кнопку «Магазин». Показывает ссылку бота и QR.
5. Привязка уведомлений: sthm показывает кнопку «Получать заявки сюда» → открывает `t.me/<bot>?start=<одноразовый код>`;
   владелец жмёт «Start» (в личке или в группе, куда добавил бота) — webhook запоминает `notifyChatId`.
6. Проверка: «Отправить тестовое сообщение».

Токен нельзя отправлять по мессенджерам — только вставлять в приложение. Если токен утёк: BotFather → `/revoke`,
вставить новый (старый перестаёт работать).

## Публичное API (новые маршруты; существующих аналогов нет)

| Метод | Путь | Что делает |
|-------|------|-----------|
| GET | `/public/tg/:slug/shop` | название магазина, категории (для заголовка и фильтра) |
| GET | `/public/tg/:slug/products` | список товаров (поиск, категория, пагинация) |
| GET | `/public/tg/:slug/products/:id` | карточка: фото, варианты, цена, наличие |
| POST | `/public/tg/:slug/orders` | создать заявку: `items[]`, `fullName`, `phone`, `region`, `district`, `comment` |
| POST | `/telegram/webhook/:slug` | апдейты бота (`/start`, привязка уведомлений); проверка `X-Telegram-Bot-Api-Secret-Token` |

Все `/public/tg/*` проверяют: магазин найден по `slug`, услуга включена, магазин не `SUSPENDED`, подпись `initData`
токеном **этого** магазина, `auth_date` не старше 24 ч. `storeId` берётся только из `slug`. DTO с `class-validator`,
размер корзины ограничен, цены из тела запроса игнорируются.

Для сотрудников (JWT, `billing-mobile`):

| Метод | Путь | Роли |
|-------|------|------|
| GET/PUT/DELETE | `/store/telegram-bot` | OWNER (+ ADMIN) — карточка / подключить / отключить |
| POST | `/store/telegram-bot/notify-link` · `/test` | OWNER — код привязки, тест-сообщение |
| PATCH | `/admin/stores/:id` (поле `telegramShopEnabled`) | ADMIN — включить/выключить услугу (существующий маршрут, как `orderAssistantEnabled`) |
| GET | `/online-orders` · `/online-orders/:id` | по правилу 6 |
| POST | `/online-orders/:id/confirm` · `/reject` | по правилу 6 |

## Не в первой версии

Онлайн-оплата; доставка; статусы заказа клиенту по ходу выполнения (кроме принят/отклонён); несколько

## Решения, раунд 2 (пользователь, 2026-11-27) — вопросов не осталось

1. Заявка — **отдельная `OnlineOrder`**.
2. Клиент создаётся/привязывается **при подтверждении**.
3. Товар без остатка показываем с пометкой **«нет в наличии»**; если есть — показываем **остаток числом** (сумма по складам магазина).
4. Область — справочник из 14 регионов, район — свободный текст.
5. Подтверждают и отклоняют заявки **OWNER, MANAGER и SELLER**.
6. Throttling публичных маршрутов — **да**, но если окажется сложным, на старте пропускаем (вернёмся, когда появится проблема).
   Библиотека `@nestjs/throttler` уже подключена; план — переиспользовать тот же `ThrottlerModule` с лимитом по IP
   на `/public/tg/*` (без отдельной инфраструктуры).
7. **Перенос между складами — отдельная фича после v1** (`billing/docs/warehouse-transfer/PLAN.md`).
8. Новый React-проект пользователь уже создал; путь к нему указать перед этапом 6.
