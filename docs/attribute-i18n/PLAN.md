## Проблема

В приложении (ru / uz / en) атрибуты и теги показываются по-английски: `slate`, `plywood`, `Length (m)`, `Wood Species`, теги `Latex`, `Cotton`, `true`, `false`.

- `Attribute.name` — одна строка без переводов. Английские имена пришли из сида (`AttributeEnum` в `prisma/seed/attribute.seed.ts`).
- `Tag` / `TagValue` — общий для всех магазинов справочник из сида (`prisma/seed/tag-seed.ts`): одежда (Material, Style, Occasion, Season, Pattern) и `New` / `Sale` со значениями `true` / `false`. Он не привязан ни к магазину, ни к направлению, поэтому магазин стройматериалов видит «Latex».
- Сейчас на проде 1 рабочий магазин и 2 тестовых — данные дешевле исправить сейчас.

## Предлагаемые решения (подтвердить)

1. **Атрибут: `name` (русский, уникальный) + `nameUz?` + `nameEn?`** — как у категорий. Клиент показывает перевод на языке приложения, если его нет — `name`.
2. **Значения атрибутов не переводим.** Это собственные имена и размеры (Оҳангарон, Grand, 9x2, 0.5). Английские значения из сида (`Red`, `Pine`, `Oak`…) переименовываем на русский, если ими пользуются, иначе удаляем. → вопрос 2.
3. **Единицы (`unit`) не переводим в БД.** Храним русскую единицу (`м`, `кг`, `л`, `шт`, `см`, `мм`, `м²`, `м³`), а мобилка переводит известные единицы своим словарём (uz: `m`, `kg`…). Неизвестную единицу показывает как есть.
4. **Переводы задаёт только платформенный ADMIN** (атрибуты и сейчас создаёт только он): поля uz/en при создании атрибута + новая правка «Переименовать / переводы» в карточке магазина → «Каталог», как `SubcategorySheet` у подкатегорий.
5. **Теги** — см. вопрос 1, от ответа зависят этапы 1–3.
6. **Обратная совместимость:** поле `name` остаётся, новые поля только добавляются. Старые версии приложения в сторах продолжат работать и будут показывать русские названия.

## Решения владельца (2026-11-22)

1. **Теги — вариант «а»**: сидовые теги (одежда, `New` / `Sale`), не стоящие ни на одном товаре, удаляются; в мобилке блок «Теги» скрывается, если тегов нет. Полноценные теги — отдельная задача.
2. **Английские значения из сида**: используемые на вариантах — переименовать на русский, неиспользуемые — удалить.
3. **`Tunika ranglar` / `Tunika razmer` остаются подключены** к магазину пиломатериалов: это будущие товары магазина (профнастил). Переводятся по общей таблице, как остальные атрибуты.

3. Закрыть открытые вопросы.

### Этап 1. Схема, миграция, сид (backend)
1. `Attribute`: `nameUz String?`, `nameEn String?`. Если в вопросе 1 выбран вариант «б» — то же для тегов и связь тег ↔ направление.
2. Миграция с данными: переименование по таблице из этапа 0 (по старому `name` → новые `name` / `nameUz` / `nameEn`), отключение ошибочных атрибутов (вопрос 3), удаление неиспользуемых сидовых тегов и значений (вопросы 1–2). Удаляем только то, на что нет ссылок (`NOT EXISTS`), поэтому на другой базе миграция ничего лишнего не тронет.
3. Сид: `AttributeEnum` → русские имена + переводы; теги — по решению вопроса 1. Иначе сид после переименования создаст английские дубли (upsert идёт по `name`).
4. **Проверка на копии прода**: восстановить последний бэкап из `~/db-backups/` в локальную временную базу, прогнать `prisma migrate deploy`, сверить результат с таблицей. Плюс прогон на чистой базе с сидом.

### Этап 2. Backend API
1. Везде, где в ответ попадает атрибут, отдавать `nameUz` / `nameEn` рядом с `name` (список файлов — в «Как сейчас»). Плоские поля вроде `attributeName` дополняются `attributeNameUz` / `attributeNameEn` (или вложенным `attributeI18n`, как `categoryI18n` у товаров — выбрать одно и применить везде).
2. `POST /category/attribute` принимает `nameUz?`, `nameEn?`.
3. **Новый** `PATCH /category/attribute/:id` (ADMIN): `name`, `nameUz`, `nameEn` (пустая строка очищает перевод), 409 при занятом `name`. Тип не меняется.
4. Теги — по решению вопроса 1.
5. Тесты: `category-attributes.service.spec.ts`, `product.service.spec.ts`. Документация: `docs/api-map.md`, `docs/features/products.md`, `billing/docs/DATABASE.md`.
